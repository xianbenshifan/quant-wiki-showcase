## 金融解释

**做什么**：把**任意布尔表达式**包装成掩码——只要表达式能对数据逐元素求值为真 / 假，就可作为本掩码使用。它是掩码体系的**逃生舱 / 扩展入口**：当现有掩码构件无法表达某个条件时，直接用表达式描述。

**为什么需要它**：掩码库只能穷举常见的判定基准（分位 / 阈值 / 时段 / 事件）。真实研究中的条件常常是跨字段、跨维度、带自定义阈值的复合逻辑（如「主动买量占成交量比例 > 某值 **且** 收盘价高于当日均价」）。与其为每个新条件新建构件，不如提供一个通用入口，让表达式直接承担判定。

**为什么它是中性构件**：表达式本身不携带收益含义——收益来源完全取决于表达式描述的命题。因此本页不标 `return_source`。

**代价**：通用入口换来的是**可读性与可复用性下降**。用具体掩码（如 [[patterns/mask/分位掩码|分位掩码]]）表达时，语义明确、可检索、可对比；用任意表达式则语义埋在表达式里。经验上：能用已命名掩码表达的，优先用命名掩码；只有在确实无对应构件时才用本页入口。

## 掩码条件

语义级：给定一个对数据逐元素求值为布尔值的表达式 $e$，掩码为

$$ m = \mathbb{1}[\,e\,] $$

- 表达式可引用任意字段、时段、自定义条件；
- 结果为布尔序列（命中 true / 未命中 NaN 或 false，按实现约定）；
- 无额外的参数化轴——判定逻辑完全由表达式承载。

## 适用场景

- **现有掩码无法表达的自定义条件**；
- **快速原型**：先验证一个复合条件的有效性，再决定是否沉淀为命名掩码；
- **跨字段复合条件**：如价量联合判定。

## 边界与陷阱

- **可复现性（工程层）**：表达式逻辑若未文档化，后续难以复现与审计；应把关键条件沉淀为命名掩码或在正文说明语义；
- **缺失值语义（计算层）**：表达式中缺失值参与比较的结果依赖实现（NaN 传播 vs 默认 false），会出现「静默全不选中」；
- **性能（计算层）**：任意表达式通常无法利用掩码库的向量化优化，大样本上可能显著变慢；
- **与命名掩码重复（概念层）**：若表达式等价于已有掩码，应改用命名掩码以保持知识库一致性。

## 可变异维度

- 表达式：任意布尔逻辑
- 结果约定：命中 true / 未命中 NaN ↔ false
